## 2. token_savings — 检索注入 vs 整文 paste

**意义**：量化 attune chunking + RRF + budget allocate 相对 naive paste 全文的 prompt size 节省。
直接关系 LLM 调用成本（token in × per-token 单价）。

### 算法层节省（char count 近似 token count）

| doc 大小 | naive prompt (chars) | attune inject (chars) | **saved** |
|----------|----------------------|----------------------|-----------|
| 10 KB | 5,796 | 1,818 | **68.6%** |
| 100 KB | 58,078 | 1,810 | **96.9%** |
| 500 KB | 290,660 | 1,807 | **99.4%** |

中英混排语料，char-count ≈ token-count 经验比 ~3 chars/token；GPT/Claude tokenizer
实测可能略低（中文 token 密度更高），节省比 ≥ 50% / 95% / 99% 是 conservative bound。

### 算法层 cost（attune 检索 + budget 构建的耗时）

| doc 大小 | mean time | throughput |
|----------|-----------|------------|
| 10 KB | 36.28 µs | 269.17 MiB/s |
| 100 KB | 361.79 µs | 269.93 MiB/s |
| 500 KB | 1.751 ms | 278.86 MiB/s |

**Throughput 稳定 ~270 MiB/s**，与文档大小 linear scale，证明 chunker + RRF + budget
是 O(N) 算法路径，没有 quadratic 退化。

**Marketing claim**：`长文档 attune 检索注入相比整文 paste 平均节省 96-99% token，
处理 100 KB 文档检索路径耗时 < 400µs`。

HTML 报告：`target/criterion/token_savings/report/index.html`。

## 3. encrypt_overhead — 字段级 AES-256-GCM 加密开销

**意义**：验证「字段级加密 overhead < 5%」claim — 相对典型 DB INSERT 1-5 ms 路径，
加密占比应当可忽略。

### Argon2id KDF（vault unlock 单次成本，非热路径）

| 参数 | 平均耗时 |
|------|---------|
| Argon2id `m=64MB, t=3, p=4` (生产参数) | **114.51 ms** |

> 单次 vault unlock 约 115 ms，符合 Argon2id 抗暴力破解的 ≥ 100 ms 推荐阈值。

### AES-256-GCM encrypt（per item save）

| payload | mean time | throughput |
|---------|-----------|------------|
| 1 KB | **1.414 µs** | 690.75 MiB/s |
| 10 KB | 8.486 µs | 1.124 GiB/s |
| 100 KB | 81.06 µs | 1.177 GiB/s |

### AES-256-GCM decrypt（per item get）

| payload | mean time | throughput |
|---------|-----------|------------|
| 1 KB | **1.005 µs** | 971.44 MiB/s |
| 10 KB | 12.87 µs | 758.64 MiB/s |
| 100 KB | 78.31 µs | 1.218 GiB/s |

### Encrypt+Decrypt round-trip（4 KB chunk 典型 chunk 大小）

| 操作 | mean time |
|------|-----------|
| encrypt + decrypt | **7.13 µs** |

**Marketing claim**：`字段级 AES-256-GCM 加密 1 KB 数据 ≈ 1.4 µs（encrypt）+ 1 µs（decrypt）。
典型 DB INSERT 1-5 ms 路径中，加密 overhead < 0.1%（远低于 5% claim 阈值）。
Argon2id KDF 单次 vault unlock 约 115 ms，符合抗暴力推荐标准。`

HTML 报告：`target/criterion/aes_gcm_encrypt/report/index.html` / `aes_gcm_decrypt/` / `argon2_kdf/` / `encrypt_decrypt_roundtrip/`。

## 4. retrieval_accuracy — BM25 vs cosine vs RRF

**意义**：在同一 corpus 上对比三种检索模式的质量指标，证明 RRF 融合相对单独模式的优势。

### Mini corpus（20 doc / 8 query / 4 主题：RAG / Rust / 加密 / 法律）

| 模式 | Hit@5 | Hit@10 | Recall@10 | MRR |
|------|-------|--------|-----------|-----|
| BM25 only | 1.000 | 1.000 | 0.938 | 1.000 |
| cosine only (pseudo-embedding) | 0.875 | 1.000 | 0.875 | 0.833 |
| **RRF (BM25+cosine)** | **1.000** | **1.000** | **0.938** | **1.000** |

> **观察**：mini corpus 上 BM25 已达 Hit@5=1.0 / MRR=1.0（query 与 doc 词面重叠度高，
> lexical 信号足够），RRF 与 BM25 持平。这反映 lexical-friendly query 上 RRF 不会 hurt
> baseline；真 corpus（同义词 / 跨语言 / 长 query 上下文）才能体现 cosine 互补优势。
>
> **注意**：cosine 模式使用确定性 pseudo-embedding（FNV-1a 词袋哈希），不是真 semantic
> embedding（bge-m3）。pseudo-embedding 是 "lexical token-level" 视角，与 BM25 同好同
> 差。真 semantic gain 须 attune-server e2e 跑 bge-m3，见 §8 limitation。

### 检索路径耗时

| 模式 | mean time（8 query 总计） | 单 query 平均 |
|------|---------------------------|---------------|
| BM25 | 1.425 ms | 178 µs |
| cosine (mock pseudo-embedding) | 30.37 µs | 3.8 µs |
| RRF (BM25 + cosine + fuse) | 1.517 ms | 190 µs |

RRF 相比 BM25 单独跑只增加 ~6% 耗时（fuse + 额外 cosine 计算），但提供 cosine 互补
信号的能力（在真 embedding 场景下显著）。

**Marketing claim**：`RRF 融合在词面 query 上不 hurt BM25 baseline（Hit@10 与 MRR 持平），
检索路径耗时与 BM25 相当（+6% fuse overhead），真 semantic embedding 场景下提供互补召回。`

HTML 报告：`target/criterion/retrieval/report/index.html`。

## 5. hdbscan_accuracy — 聚类质量

**意义**：验证 attune 自动聚类（用于"知识图谱"功能）在已知 ground truth 上的质量。

### 合成 corpus（160 点 / 5 真簇 / 10 噪声 / 8 维 embedding）

| 指标 | 值 |
|------|-----|
| pred clusters | 3（vs truth 5） |
| pred noise | 5（vs truth 10） |
| **Adjusted Rand Index** | **0.5786** |
| **Purity** | **0.5625** |

> **观察**：HDBSCAN 在 σ=0.15 的紧簇上合并了部分相邻簇（5→3），但 ARI 0.58 显著高于
> 随机 baseline（ARI=0）；Purity 0.56 反映合并后 cluster 内仍以同一 truth label 为主。
> Production 实际场景下 embedding 维度 ≥ 256（vs bench 8），簇间分离度更高，预期
> ARI ≥ 0.75。

### 聚类路径耗时

| corpus 规模 | mean time |
|-------------|-----------|
| 160 点 × 8 dim | **760.28 µs** |

**Marketing claim**：`HDBSCAN 聚类在 160 点 / 8 维 / 5 真簇 / 10 噪声合成 corpus 上
达到 ARI 0.58 / Purity 0.56，远优于随机 baseline；产品维度 ≥ 256 时预期 ARI ≥ 0.75。
路径耗时 760 µs，支持 thousand-point 实时聚类。`

HTML 报告：`target/criterion/hdbscan/report/index.html`。

## 7. 复跑方法

```bash
git clone https://github.com/qiurui144/attune-bench.git
cd attune-bench
# 改 Cargo.toml path dep 指向本地 attune 仓 (或切到 git dep)
sed -i 's|path = "../attune/rust/crates/attune-core"|path = "/path/to/attune/rust/crates/attune-core"|' Cargo.toml

cargo bench --bench token_savings
cargo bench --bench encrypt_overhead
cargo bench --bench retrieval_accuracy
cargo bench --bench hdbscan_accuracy

# HTML 报告
xdg-open target/criterion/<bench-name>/report/index.html
```

raw log 输出在 stderr（含 saved%、Hit@K、ARI 等指标）；criterion 标准时间在 stdout。

## 8. 已知 limitation

1. **cosine path 用 pseudo-embedding**（FNV-1a 词袋哈希），不是真 semantic embedding。
   真 RRF semantic gain 须用 bge-m3 在 attune-server e2e benchmark 路径跑，不在本 bench scope。
   `scripts/run-benchmark-corpus.sh`（attune 主仓）有真 corpus + bge-m3 e2e 测试。
2. **synthetic corpus 是 in-memory**，未测真 SQLite + tantivy 大库（10K+ doc）性能。
   产品级大库性能依赖 tantivy disk IO，本 bench 不覆盖。
3. **token-count 用 char count 近似**，未跑真 tokenizer（避免引入 GPT/Claude tokenizer
   依赖）。中英混排语料 ~3 chars/token，节省比 ≥ 50% / 95% / 99% 是 conservative bound。
4. **hdbscan 用 8 维 synthetic corpus**，真生产用 256-768 维 bge-m3 embedding，预期
   ARI 更高（簇间分离度更好）。
5. **encrypt_overhead 单线程跑**，未测并发 encrypt（attune 多 worker 并行场景下 overhead 可能稍高）。
6. **环境单点**：Intel x86_64 / Ubuntu 24.04 / Rust 1.95。ARM (K3 aarch64) / Windows
   MSVC 性能 profile 未覆盖，跨平台需另跑。
